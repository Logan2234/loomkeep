## Changements de comportement à connaître

Les changements suivants s’appliquent même sans migration de logique métier :

- **Assets Node** : seuls les fichiers connus au build sont servis. Ajouter ou remplacer un fichier dans l’image déjà construite n’est plus une méthode de configuration ; les variables publiques restent injectées à l’exécution. Les ETag remplacent `Last-Modified`, et les assets acceptent GET/HEAD.
- **Origine publique** : `ORIGIN` et `prerender.origin` sont remplacés par `paths.origin`. Loomkeep ne configure aucun des anciens réglages dans le web. `WEB_ORIGIN` reste un réglage de l’API ; il ne doit pas être renommé. Les configurations personnalisées de self-hosters qui ajoutaient `ORIGIN` doivent suivre la nouvelle API.
- **Navigation** : un lien vers l’URL courante relance les chargements de SvelteKit ; `goto` refuse une URL sans route correspondante. Les cibles fixes utilisées par Loomkeep existent. Le `redirectTo` de connexion est une entrée libre validée pour son origine, pas une garantie d’existence de route : une URL interne inconnue peut désormais rejeter la navigation.
- **Erreurs** : `handleError` reçoit aussi les erreurs attendues et de rendu. `@sentry/sveltekit@11.2.0`, déjà installé, distingue les catégories d’erreur de Kit 3 ; pas de bump Sentry dans cette PR.
- **MSW en Node** : pas de cookie jar synthétique. Les tests qui veulent un cookie doivent le fournir explicitement et lire `cookies` dans le resolver. Aucun handler existant n’utilise l’ancien accès synthétique via `request.headers.get('cookie')`.
- **Timers MSW** : plus de contournement des faux timers. Les tests existants à faux timers ne retardent pas des réponses avec `delay()` ; aucun ajustement de temporisation n’est requis.

## Prérequis déjà satisfaits

TypeScript 6.0.3, Svelte 5.57.1, Vite 8.3.2, vite-plugin-svelte 7.3.1, Docker Node 26 et CI Node 22 répondent aux contraintes. La configuration SvelteKit est déjà dans le plugin Vite. Le frontend est ESM et n’utilise pas `require('msw')`.

Pas de modification du schéma Prisma, de migration SQL, des données utilisateur, du contrat NestJS ni des noms de cookies d’authentification. Les cookies de session sont gérés par l’API, pas par des actions SvelteKit.

## Ruptures amont sans usage trouvé dans Loomkeep

Ces API ont été recherchées dans le frontend et les configurations ; leur absence évite un correctif dans cette migration.

| Groupe                       | API / comportement examiné                                                                                                                                                                                                                   |
| ---------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Kit : imports retirés        | `$app/stores`, `$service-worker`, `$app/paths` : `base`/`assets`/`resolveRoute`, `@sveltejs/kit/node/polyfills`.                                                                                                                             |
| Kit : types déplacés         | `Page`, `ReadonlyURLSearchParams`, types remote, types de configuration d’environnement, `defineParams`, anciens `Pathname`/`Asset`. `ReadonlyURL` et `Handle` sont traités dans les adaptations effectives.                                 |
| Kit : options retirées       | `files.lib`, `preloadStrategy`, `experimental.handleRenderingErrors`, `experimental.instrumentation`, `experimental.tracing`, `csrf.checkOrigin`.                                                                                            |
| Kit : actions et remotes     | `use:enhance`, `fail`, actions vers une autre page, formulaires remotes, mutations single-flight, accès `event.url`/`params`/`route` dans les remote queries, fichiers et dossiers remotes. Loomkeep utilise des mutations REST vers NestJS. |
| Kit : navigation avancée     | Consommation du résultat de `preloadData`, `delta`, shallow routing, `invalidateAll`, valeurs `data-sveltekit-*="off"`, appels `resolve`/`asset`, redirections serveur externes.                                                             |
| Kit : serveur et réponse     | Serveur Node/adaptateur personnalisé utilisant `getRequest`/`setResponse`, `Server`, `SSRManifest`, `createEntries`, `generateManifest`, instrumentation serveur. Pas d’endpoint SvelteKit 204 ni de `error(status, object)`.                |
| Kit : organisation et config | Import client de dossiers `server`, anciens matchers `src/params/`, exports `config` concurrents universel/serveur, types `CookieParseOptions`/`CookieSerializeOptions`, noms de cookies non ASCII.                                          |
| MSW : points d’entrée        | `msw/native`, GraphQL, `GraphQLLinkHandlers`, `handleRequest`, extension réseau personnalisée. La dépendance indirecte Vitest est traitée séparément.                                                                                        |
| MSW : navigateur/WebSocket   | `setupWorker`, `worker.stop`, listeners MSW de WebSocket `connection`, option WebSocket `onUnhandledRequest` devenue `onUnhandledFrame`. Le renommage du réglage HTTP des tests est traité dans les adaptations effectives.                  |
| MSW : requêtes particulières | `file://`, upgrade HTTP-vers-WebSocket par `fetch`, `bypass()` et sa gestion du `Content-Length`. Aucun usage applicatif ou test concerné.                                                                                                   |

## Vérification

- Le premier test du serveur compilé a échoué sur l’absence d’assets dans le précache ; ce test reste dans `scripts/production.spec.mjs`.
- Build web réussi. Les 6 tests du serveur compilé et les 26 tests ciblés MSW/worker/hooks/client API/helpers passent. Les hooks sont vérifiés pendant la préparation de la PR ; leur statut final exact est indiqué dans sa description.
- La CI de la PR doit vérifier les suites existantes, la production web, les tests du serveur, le contrat OpenAPI, les images Docker et les autres contrôles. Un build local ne démontre pas à lui seul une validation navigateur, CI ou déploiement.
- Avertissement préalable indépendant : `openapi-typescript@7.13.0` déclare encore TypeScript 5 comme peer alors que le projet utilise déjà TypeScript 6. Cette migration ne masque pas cet avertissement.
